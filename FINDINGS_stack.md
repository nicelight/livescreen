# Findings LiveScreen

## 1. Подавление критических ошибок записи

**Сложность:** 6/10<br>
**Важность:** 10/10<br>
**Статус:** `fixed`

Ранее в [src/recorder.rs](/home/serg/Projects/Desktop/livescreen/src/recorder.rs) и `src/main.rs` игнорировались ошибки `set_state`, отправки `EOS`, остановки pipeline и сохранения настроек.

Риск: приложение может показать, что файл сохранён, хотя MP4 повреждён или настройки не записались.

Предложение: проверять результаты операций и передавать понятные ошибки в UI. Особенно важно обработать `EOS`, перевод pipeline в `Null` и сохранение файла. Исправление средней сложности.

## 2. Возможен panic при запуске recorder thread

**Сложность:** 4/10<br>
**Важность:** 8/10<br>
**Статус:** `fixed`

Ранее при запуске recorder thread использовался `.expect("recorder thread")`; теперь `start_recorder` возвращает `Result`.

Риск: ошибка ОС при создании потока завершит приложение вместо сообщения пользователю.

Предложение: изменить `start_recorder` на возврат `Result<RecorderHandle>`, показать ошибку в статусе и вернуть кнопку записи в рабочее состояние. Исправление небольшой или средней сложности.

## 3. Ошибки конфигурации скрываются

**Сложность:** 6/10<br>
**Важность:** 7/10<br>
**Статус:** `fixed`

Ранее `read_json` в `src/main.rs` молча заменял повреждённый конфиг значениями по умолчанию. Теперь загрузка и атомарная запись находятся в `src/configuration.rs`.

Риск: пользователь может потерять настройки и не понять причину; вручную изменённые значения могут работать непредсказуемо.

Предложение: добавить проверку диапазонов, контекстные сообщения об ошибках, безопасную атомарную запись и уведомление в UI. Исправление средней сложности.

## 4. Запись не завершается надёжно при закрытии приложения

**Сложность:** 8/10<br>
**Важность:** 9/10<br>
**Статус:** `fixed`

Recorder теперь владеет единым lifecycle сессионной записи и коррелирует все команды и события через `RecordingSessionId`. При закрытии окна GTK неблокирующе отправляет `Stop`, блокирует повторное закрытие и завершает приложение только после `Stopped`, `Error` или `Cancelled`.

Для `Stopped` recorder требует подтверждённые EOS, `Null` и существующий итоговый файл. Ожидание выполняется только в recorder worker; GTK main thread не ждёт pipeline или `JoinHandle`.

Регрессионные сценарии переходов и корреляции сессий покрыты unit-тестами; реальный Wayland shutdown smoke test остаётся ручным ограничением.

## 5. Гонка preview pipeline при смене камеры

**Сложность:** 7/10<br>
**Важность:** 7/10<br>
**Статус:** `need fix`

При смене камеры старый preview pipeline останавливается асинхронно, а новый может запускаться до завершения старого.

Риск: одновременная работа с одним `/dev/video*`, гонки переходов в `Null` и нестабильное отображение кадров.

Предложение: безопасно сериализовать остановку старого и запуск нового pipeline, не блокируя GTK main thread.

## 6. Дальнейшее разделение application shell

**Сложность:** 6/10<br>
**Важность:** 5/10<br>
**Статус:** `need fix`

`src/main.rs` остаётся крупным composition root с тесно связанной UI state machine и lifecycle callbacks.

Риск: дальнейшие изменения GTK lifecycle и состояния записи сложнее проверять из-за высокой связанности application shell.

Предложение: выделить только те части application shell, которые улучшают тестируемость или изоляцию lifecycle, сохранив `main.rs` точкой сборки приложения.
